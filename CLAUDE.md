# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Rust bindings (via `cxx`) for the C++ NIF library [ousnius/nifly](https://github.com/ousnius/nifly), vendored as a git submodule at `nifly-sys/vendor/nifly`. Never edit vendored files.

## Commands

```sh
git submodule update --init                 # first checkout
cargo build
cargo nextest run --workspace               # all tests (cargo install cargo-nextest --locked)
cargo nextest run --workspace --features mint   # also the mint conversions
cargo nextest run set_shape_order::         # one test module (tests/it/<name>.rs)
cargo nextest run shader::shader_hierarchy  # one test
cargo test --doc                            # doc tests, which nextest skips
cargo clippy --all-targets                  # the build.rs `&bridge_files` warning is known
RUSTDOCFLAGS="-D warnings" cargo doc --no-deps --workspace
UPDATE_HIERARCHY=1 cargo nextest run type_hierarchy::   # regenerate the module type hierarchies
UPDATE_TYPE_DOCS=1 cargo nextest run type_docs::   # regenerate docs/types/
./scripts/format.ps1 [-Check]               # clang-format the shims (non-vendored C/C++)
cargo run --example stats assets/Suzanne.nif
cargo run --release --example check_assets [-- --verbose] [path]   # defaults to external_assets/
```

## `external_assets/` is off-limits for commits

It holds meshes extracted from Skyrim and is gitignored for legal reasons. Never commit, copy into `assets/` or `tests/`, or paste its contents. Use it only for local checks (`check_assets`, throwaway examples you delete afterwards). Tests use `assets/*.nif` (described in `assets/README.md`) and nifly's own test files in `nifly-sys/vendor/nifly/tests/{input,expected}`.

## Architecture

**Two crates.** `nifly-sys` holds the raw `#[cxx::bridge]` modules plus C++ shims; the root crate `nifly` is the safe API. File-level methods live on `NifFile` (`src/file.rs`); per-block methods on the `View`/`Edit` handles (`src/handle.rs`).

**`NifFile` sections.** `NifFile`'s file-level methods are split into inherent `impl NifFile` blocks, one per topic module:

| Section | Module |
|---|---|
| General: I/O, optimizing, sorting, block lookup and walking, extra data | `file.rs` |
| Nodes | `nodes/mod.rs` |
| Shapes | `geometry/mod.rs` |
| Shaders, materials and textures | `shaders/mod.rs` |
| Collision | `collision/mod.rs` |
| Animation | `animation/mod.rs` |

- Put a new method in its topic's block.
- Each block opens with a `# Heading` doc comment, which rustdoc shows as a section.
- Rustdoc orders the sections by the `mod` order in `lib.rs`.
- Keep the "Methods by topic" list in `NifFile`'s doc in step.
- Shared index helpers (`block_index_to_ffi`, `index_from_ffi`) are `pub(crate)` in `file.rs`.
- Don't use extension traits for `NifFile`: they need imports and hide the methods in rustdoc.

**Bridges and shims (`nifly-sys`).**
- One bridge per area in `nifly-sys/src/*.rs`. Every bridge file must be listed in `bridge_files` in `nifly-sys/build.rs`. `NifFile`'s own bridge is split three ways: `nif_file.rs`, `nif_file_extra_data.rs` (the `assign_*` shims) and `nif_file_refs.rs` (`RefKind`, `RefList` and the ref shims).
- Types shared across bridges are aliased (`type NiShape = crate::geometry::ffi::NiShape;`).
- Shims are header-only `inline` functions in `nifly-sys/include/*_shim.h`, namespace `nifly_rs`.
- Large shims are split into parts, kept flat in `include/`. `<area>_shim.h` is the header bridges and other shims include. It holds the casts, shared macros and helpers, then includes its parts `<area>_shim_<topic>.h` at the end, in dependency order, inside `// clang-format off/on` so include sorting can't reorder them. Each part includes its umbrella and holds whole items moved from it. `#undef`s of shared macros go after the part includes. The only `.cpp` files are `src/read_bridge.cpp`, `src/write_bridge.cpp` and `src/private_access.cpp`, which reaches private fields that have no accessors (`NiPathInterpolator`) through explicit template instantiation, once for the whole program.
- nifly methods that are non-const but only read are wrapped with `const_cast`.
- Lists of pointers become count + getter shims or `rust::Vec`. Strings become `rust::Slice<const uint8_t>`, or `UniquePtr<CxxVector<CxxString>>` for lists.
- Upstream methods that are templates (e.g. `FindBlockByName<T>`) can't be bound and are reimplemented in Rust.

**API coverage tracking.** The `NifFile` method list in `nifly-sys/src/nif_file.rs` is kept as comments marking each upstream method as bound directly, bound through a shim, reimplemented in Rust, or not bound. Update it when exposing a method.

**Class hierarchy.**
- Each nifly class is a `#[repr(transparent)]` newtype generated by `ni_types!` (`src/macros.rs`).
- Large topic modules are folders: `mod.rs` holds the module docs, the `ni_types!` block (its newtypes' field is private to the defining module, so only `mod.rs` and its submodules can use it), shared private helpers and macros, and the `impl NifFile` section. Private submodules start with `use super::*;` and `mod.rs` re-exports them with `pub use self::<sub>::*;`, so public paths stay `nifly::<area>::X`. Helpers used by sibling submodules go in `mod.rs` or become `pub(super)`.
- `Deref` goes to the direct C++ base through an `upcast_*` shim, and `DerefMut` to the same object (`objects::upcast_mut`), so a `&mut` subclass reaches its bases' setters.
- A sealed `NiType` impl supports `NiObject::downcast::<T>()` and `NifFile::blocks_of::<T>()` through a `dynamic_cast` `downcast_*` shim.
- The C++ side generates those shims with per-module macros (`NIFLY_RS_NODE`, `NIFLY_RS_SHADER`).
- Rust names treat acronyms as words: `BSFadeNode` → `BsFadeNode`, `NiAVObject` → `NiAvObject`.
- Each module's docs end with a `# Type hierarchy` section: nested lists of links generated from the `ni_types!` entries between `type-hierarchy` markers. `tests/it/type_hierarchy.rs` fails when they're stale; rerun it with `UPDATE_HIERARCHY=1` after adding types.

**Math types.** `object3d::{Vec3, Matrix3, Transform}` are plain Rust types with their own math, unlike the block types, which wrap C++ objects. They convert to and from the bridge's shared structs with crate-private `to_ffi`/`from_ffi` at each call. The `mint` feature adds conversions for `Vec3` and `Matrix3`.

**Borrowing and indices.**
- Blocks are handed out as `&T` borrowed from `&NifFile`, or as `&mut T` from `NifFile::block_of_mut::<T>(index)` (or `block_mut(index)` plus `NiObject::downcast_mut`).
- Naming: the plain name returns the base type (`block`, `blocks`, `children`), `_of::<T>` takes a type (`block_of`, `blocks_of`, `children_of`), and `_mut` goes last (`block_of_mut`). `find_block_by_name::<T>` is the one generic method without `_of`.
- Every `NifFile` method returning a block has a `_mut` form, taking block indices where the shared form takes references. One returning a `View` returns an `Edit` (`root_node_mut`). One returning `&T` returns `&mut T` (`block_of_mut`, `find_block_by_name_mut`) through the crate-private `NifFile::find_mut`, which takes a closure doing the shared lookup and builds the `&mut` from the `object_mut` shim's pointer (through `Pin<&mut NifFile>`), never from the shared reference.
- Handing out `&mut T` for C++ objects is sound because every wrapper is zero-sized (cxx's opaque types are), so safe code can't move one: `mem::swap` copies nothing. `ni_types!` asserts the size (`objects::assert_zero_sized`); keep that assert on hand-written wrappers. `Pin` stays inside the crate: `ffi_mut()` pins for the bridge. Don't add `impl Unpin`. Use `objects::reborrow_mut` for new `&mut` casts, which keeps the `&mut`'s provenance.
- Per-block setters go on the block type as `&mut self`, calling shims through the macro's `ffi_mut()` (see `NiMaterialProperty`). Put a setter on the type that has the field, not on subclasses: callers reach it through `DerefMut`. A subclass setter with a base setter's name hides it (`NiCamera::set_raw_flags`); callers reach the base one through a `&mut Base` binding.
- Block-specific methods that follow the block's refs or check other blocks go on the handles in `src/handle.rs`: `impl View<'_, T>` (holds `&NifFile`, derefs to `T`) and `impl Edit<'_, T>` (holds `&mut NifFile`, also derefs mutably to `T`, for its setters; `View` methods via `view()`), in `T`'s topic module, not on `NifFile`. Reach them with `NifFile::view`/`edit::<T>(index)` or `BlockIter::views`. An `Edit` getter reborrows (`fn x(&mut self) -> Option<Edit<'_, U>>`) instead of a `_mut` form. File-level operations stay on `NifFile`.
- Each block type's docs end with generated *Type hierarchy* (its supertypes and subtypes) and *Handle methods* (every `View`/`Edit` method that works on it, including its bases') sections. `ni_types!` includes them from `docs/types/<Type>.md` (the `objects.rs` bases with their own `#[doc = include_str!]`). `tests/it/type_docs.rs` builds the files from the `ni_types!` entries and each method's impl target or `where T:` bound, and fails when they're stale; rerun it with `UPDATE_TYPE_DOCS=1`. A new type's file must exist before the crate compiles, so create it empty first. The test also requires:
  - a `T:` bound on every public method of a generic handle impl;
  - names unique per handle, private helpers included, so each doc link names one method (`skin_data`, `psys_shader` rather than `data`, `shader` again);
  - a doc summary on every type with handle methods.
- Marker traits for handle bounds (`HasKeyData`, `HasInterpolator`, ...) are implemented with `impl Trait for X {}`, `impl_marker! { Trait: A B }` (`macros.rs`) or `chained_modifier!`, the forms the test parses.
- Shape methods are on the exact type, `impl View<'a, NiShape>` / `impl Edit<'_, NiShape>` (subtypes `upcast` first), not generic: names like `triangles`, `vertex_colors` and `segments` would hide `NiSkinPartition`, `NiPalette` and `BsSegmentedTriShape` getters. Methods that read another file take a `View` of the source (`Edit::apply_locked_normals`, `NifFile::clone_shape_from`).
- Methods for a base type and its subtypes are generic: `impl<T: NiType> View<'_, T>` with `where T: IsA<NiNode, I>` (`objects::IsA`, inferred through each wrapper's `HasParent`). They apply to every `View<T>` and hide a block method of the same name, so block getters and setters don't reuse handle method names (`index`, `file`, `get`, `cast`, `children`, `parent`, `extra_data`, ...).
- Mutating `NifFile` methods take `&mut self`, so they can't take a `&NiNode` from the same file. They take block indices instead: `file::Index` (= `usize`).
- Use `Index` only for block indices. Counts, slots and bone positions stay `usize`.
- Block iterators are `iter::BlockIter<'a, T, I>`. They hold the file, a source of block indices and the type to downcast to. They have `.indexed()`, `.indices()` and `.of::<U>()`. Use these instead of `block_index`, which is an O(blocks) search.
- nifly's `NIF_NPOS` / `u32::MAX` means "none"; convert with `block_index_to_ffi` and `index_from_ffi`.
- Methods taking a block reference start with `debug_assert!(self.contains(x), "... does not belong to this NifFile")`.

**I/O.**
- No `std::filesystem::path` APIs.
- `NifFile::load` takes any `Read`; `save` takes `Write + Seek`, because nifly seeks back to patch block sizes.
- `RustReader`/`RustIStream` and `RustWriter`/`RustOStream` adapt them to C++ streams. The first `io::Error` is stored and surfaced as `Error::Io`.
- `NifFile` has no move ctor, so shims create it with `make_unique` and load in place.

## API conventions

- Names and paths are `impl AsRef<[u8]>` in and bstr types out: `&BStr` borrowed, `BString` owned. They're never decoded, since files are often Windows-1252, and callers convert. `bstr` is re-exported as `nifly::bstr`. Don't take `AsRef<BStr>`: byte literals, `String` and `Vec<u8>` don't implement it. Binary blobs (cloth and collision data) stay `&[u8]`.
- Root re-exports are only the entry points: `NifFile`, `NifVersion`, `Error`, `NifResult`. `prelude` adds the common, distinctly named types (file types and options, `View`/`Edit`, the `objects` bases, `NiNode`, `NiShape`, the math types) and `bstr::ByteSlice as _`. Keep generic names (`Error`, `Key`, `Plane`) and block subtypes out of it; `tests/it/prelude.rs` checks a load, edit and save with only the prelude. No game-specific preludes: each `NifVersion` constant's docs list the types its game uses, naming top-most types and only what the crate's docs state about that game.
- `rustfmt.toml` sets `reorder_modules = false`, since `lib.rs`'s `mod` order sets `NifFile`'s doc section order.
- Load, save and optimize options are passed as `Option<T>`, with `Default` matching nifly's defaults.
- Extra data goes through one `Edit::assign_extra_data(impl IntoExtraData)`. The value newtypes (`ExtraString`, `ExtraFloat`, `ExtraBsxFlags`, …) carry their own name. Existing blocks change through their setters (`set_value`, `set_name`, …), which share the C++ fill code with the assign shims (`extra_data_shim.h`).
- Flag fields use `bitflags` types declared with `const _ = !0` (files set bits without names) and built with `from_bits_retain`, so unnamed bits survive. Packed fields with enum-valued sub-fields (`AlphaFlags`) stay hand-written newtypes; flags whose meaning is unknown stay raw integers, and accessors returning or taking a raw integer have `raw_flags` in their name (`raw_flags`, `data_raw_flags`, `set_raw_flags_1`).
- Each exposed method gets an integration test in `tests/it/`. The tests are modules of one binary (`tests/it/main.rs`), so the library links once; add new files there as `mod`s, and use `tests/it/common.rs` for the shared `load`, `upstream`, `save` and `reload`. Test behaviour, not a file's fixed layout, downcasts or every bit of a flags type.
- Keep READMEs terse.

## Validation

Protect well-established logic with checks, but don't over-constrain what callers can do at the edges of specific versions.

- **Validate when the rule holds in every version.** Examples: indices in range, one value per vertex, counts that must match their arrays, references to blocks of the right type, no cycles. Also validate anything that would crash, throw or write out of bounds. Where nifly fails silently or corrupts data on such input, check in Rust or a shim. Return `bool`/`Option` and change nothing on failure (see `set_shape_order`, `Edit::set_parent`, `Edit::set_triangles`). Keep values nifly writes from separate fields in step (`set_texture_arrays` keeps the stored count).
- **Document, don't block, when it depends on the version.** Examples: a field only some games save, a value a version can't represent, a nifly save quirk for one version. Write the data and say what happens to it: lost on save, renumbered, misread. Callers decide what to check (see `NiGeometryData::set_consistency`, the `BsLightingShaderProperty` fields, and `set_shader_type`'s Fallout 76 and Starfield section).
- **Still fix side effects that don't restrict callers.** For example, saving shouldn't change the file in memory (`LightingTypeRestore` in `nif_file_shim.h`).
- **A version-specific check is fine when the result can't be a valid file for that version at all.** Examples: a count that overflows the width the version stores it in (`triangle_limit` in `Edit::set_triangles`), or a block type the game doesn't have (`create_shape` refusing Oblivion). Anything the game could still read is documented instead.
- **Return values describe the call, not the data.** `false`/`None` means the call was rejected and nothing changed.

## Doc comments

Public docs in `src/` describe the bindings' own behaviour, as if nifly and the bindings were one library.
- **Don't mention nifly or upstream.** No "Same as nifly's `X`", C++ signatures, C++ enum or class names, deprecated C++ aliases, or how upstream behaves without our checks. NIF block types like `BSTriShape` are file-format terms and are fine.
- **Write tersely.** A summary line, then conditions and caveats only if needed. Keep return values, side effects (block indices change), panics and real caveats. Leave out remarks on names or implementation.
- **Stay in crate scope.** Don't explain standard library or other external items, such as which readers and writers work or that `&mut reader` can be passed. Assume readers know them. Examples may still use them.
- **Foreign blocks:** "Panics in debug builds if `shape` is from another file; in release builds the result is meaningless."
- **Exceptions:** `nifly-sys`, private helpers and `//` implementation comments may name the C++ they wrap.

## nifly behaviours to know

- Load runs `PrepareData`, which normalizes texture paths.
- Save may optimize (drops unreferenced blocks and empty refs) and sort blocks, which changes block indices. It also rebuilds the string table.
- `DeleteNode` leaves `NiSkinData` out of sync.
- `optimize_for` and `set_shape_order` replace and re-sort blocks.
- `NiSourceTexture` mishandles embedded textures' pixel data ref from 10.0.1.4 on. `load_nif` swaps in a replacement factory (`SourceTextureFactory`) and `save_nif` uses `SourceTextureRestore`, both in `nif_file_shim.h`.
- `BSPackedCombinedSharedGeomDataExtra` reads each object's vertices and triangles, which only the baked `BSPackedCombinedGeomDataExtra` stores. `load_nif` registers `PackedSharedGeomDataFactory` and `assign_packed_shared_geom` creates `PackedSharedGeomData`s, which use the shared layout (`extra_data_shim_packed_geom.h`).
- Writing an Oblivion file clears each `NiGeometryData`'s tangent flag in memory, so the next save would drop the tangents' `NiBinaryExtraData`. `save_nif` undoes it with `TangentFlagRestore` (`nif_file_shim.h`).
- `BSGeometry` mesh data is written with positions as 16-bit fractions of its `scale`, which nifly doesn't update, and writing drops the second UV set and cuts the first to 65535 entries. `load_nif` registers `GeometryFactory`, whose `Geometry`s write internal meshes with `write_mesh_data` (`mesh_writer.h`), also used for external `.mesh` files. It writes `scale` widened where the positions need it (`fitted_mesh_scale`), leaving the mesh unchanged.
- A string reference read from a file keeps its string table index, so an empty string saves as an empty entry; a new one with empty text saves as no string. List setters keep the old reference where the text is unchanged (`set_text_keys`, `set_morphs`).
- `NiBlendInterpolator` doesn't list its items' interpolator refs as child refs, so saving would drop those interpolators and renumbering blocks would leave the refs stale. `load_nif` registers `BlendInterpolatorFactory`, and the add shims create `BlendInterpolator`s, which list them (`animation_shim_interpolators.h`).
- `NiFloatExtraDataController` reads and writes its extra data name in every version, but files store it only from 10.2.0.0. `load_nif` registers `FloatExtraDataControllerFactory` and the add shim creates `FloatExtraDataController`s, which sync it by version (`animation_shim_controllers.h`).
- Some particle blocks read and write fields in every version that early Oblivion files (10.1.0.106, 10.2.0.0) don't store: emitters' radius variation (from 10.4.0.1), four `NiPSysRotationModifier` fields (from 20.0.0.2) and `NiMeshPSysData`'s pool fields (from 10.2.0.0). `load_nif` registers `ReplacementFactory`s and the add shims create the replacements (`Emitter<T>`, `RotationModifier`, `MeshPSysData`), which sync them by version (`particles_shim_replacements.h`).
- `NiSpotLight` reads and writes its inner angle in every version, but files store it only from 20.2.0.5. `load_nif` registers `SpotLightFactory` and the shims create `SpotLight`s, which sync it by version (`effects_shim.h`).
- Files before 10.1.0.104 store a sequence's accumulation root name and text keys ref after its name, which `NiSequence` doesn't read. `BSAnimNote` reads and writes gain and state for grab IK notes too, which nif.xml saves only for look IK notes. `load_nif` registers `ReplacementFactory`s and the add shims create the replacements (`Sequence`, `ControllerSequence`, `AnimNote`), which follow the file layout (`animation_shim_sequences.h`).
