# Design

nifly-rs binds the C++ library [nifly](https://github.com/ousnius/nifly) to Rust. This file explains
how the bindings are built and why. [CLAUDE.md](CLAUDE.md) has the day-to-day rules and commands.

## Goals

- **A safe API:** no `unsafe` for callers, with Rust ownership in place of C++ pointers.
- **Every game, Morrowind to Starfield:** the bindings never narrow what nifly reads or writes.
- **Files round-trip:** what loads saves back unchanged, including blocks of unknown types.
- **Load and save are always correct.** Where nifly misreads or miswrites a block, the bindings
  fix it without editing nifly (see [Fixing nifly without editing it](#fixing-nifly-without-editing-it)).

## Layers

```text
nifly (C++, vendored submodule, never edited)
  └ nifly-sys/include/*_shim.h  C++ shims: inline functions in namespace nifly_rs
    └ nifly-sys/src/*.rs        #[cxx::bridge] declarations of the shims
      └ src/                    the safe API: block types, NifFile, View/Edit handles
```

cxx can't bind much of nifly directly:
- templates (`FindBlockByName<T>`), overloads and default arguments;
- methods that only read but aren't `const`;
- containers of pointers, `std::filesystem::path`, and nifly's own string types.

Each shim turns one such method into a function cxx can declare. It returns counts and getters
for lists, byte slices for strings, and `Read`/`Write` adapters for streams. The shims also hold
the checks and fixes that have to run inside C++. The cost is that a simple getter exists three
times (shim, bridge declaration, Rust method), which is most of why the bindings are larger
than nifly.

## Block types

- **Newtypes:** each nifly class is a `#[repr(transparent)]` newtype over cxx's opaque type,
  generated by `ni_types!`. About 390 types.
- **Inheritance:** `Deref` goes to the direct C++ base through an `upcast_*` shim, so a
  `&BsTriShape` reaches `NiShape`, `NiAvObject` and `NiObject` methods. `DerefMut` does the
  same for setters.
- **Downcasting:** a sealed `NiType` trait backs `NiObject::downcast::<T>()` and
  `NifFile::blocks_of::<T>()`, through a `dynamic_cast` shim per type.
- **Generic methods:** `IsA<Base, I>` (inferred along the `Deref` chain) bounds methods that
  apply to a base type and all its subtypes.
- **Why `&mut T` is sound:** every wrapper is zero-sized, so safe code can't move a C++ object
  out from under nifly. `mem::swap` on two `&mut NiNode` copies nothing. `ni_types!` asserts
  the size, and `Pin` stays inside the crate.

## Borrowing

- **Blocks hold no references:** `&NiNode` is borrowed from `&NifFile`. A block on its own can't
  reach other blocks.
- **Handles reach other blocks:** what follows refs (a shape's shader, a node's children, a
  skin's bones) lives on `View<'a, T>`, which pairs a block with `&NifFile`, and `Edit<'a, T>`,
  which pairs it with `&mut NifFile`. Plain getters and setters stay on the block type and are
  reached through the handles' `Deref`.
- **Mutating calls take indices:** `&mut NifFile` can't coexist with a `&NiNode` from the same
  file, so mutating methods take block indices (`file::Index`) instead of references.
- **Iterators carry indices:** `BlockIter` yields blocks with their indices, so callers never
  search for an index (`block_index` is O(blocks)).

## Values

- **Names and paths are bytes:** `&BStr` out, `impl AsRef<[u8]>` in. Files are often
  Windows-1252, so the bindings never decode them.
- **Flags:** `bitflags` types that keep unnamed bits, so files round-trip. Flags whose meaning is
  unknown stay raw integers named `raw_flags`.
- **Math:** `Vec3`, `Matrix3` and `Transform` are plain Rust types with their own math, converted
  to and from the bridge at each call. The `mint` feature adds conversions.
- **Options:** load, save and optimize options are `Option<T>`, whose `Default` matches nifly's.

## Validation

- **Rules that hold in every version are checked:** indices in range, counts matching arrays,
  refs to the right block type, no cycles, and anything that would crash or write out of
  bounds. A rejected call returns `false` or `None` and changes nothing.
- **Version-dependent rules are documented, not enforced:** for example, a field only some games
  save. The bindings write the data and say what saving does with it.
- **Check only what can't be valid for any game:** callers working at the edges of a version
  shouldn't be blocked by the bindings.

## Fixing nifly without editing it

nifly is a git submodule tracking upstream and is never edited, so updating it stays a
submodule bump. Some nifly blocks are read or written wrongly in some versions, and its save
changes the file in memory. The bindings fix these in the shims with three mechanisms. If nifly
fixes a bug, the matching workaround can be removed.

### Replacement factories: blocks misread on load

nifly creates each block on load through a factory registered under the block's name. When a
block's read code doesn't match the file layout, the stream goes out of step: that block's
later fields, and often every block after it, are garbage by the time `load` returns. A fix
after loading can't recover them, so the fix has to be in the read itself.

The fix uses replacement classes:
- Each subclasses the nifly class and overrides `Get`/`Put` (read/write) to follow the real
  layout for each version.
- `load_nif` swaps their factories into nifly's registry. The registry is protected, and
  `FactoryAccess` reaches it.
- The shims that add blocks create replacements too, so new blocks also write correctly.
- They override `Clone_impl`, so cloned blocks stay replacements.

The **Evidence** column says how each bug was established:
- **Real files:** seen when loading and saving nifly's own test files.
- **Built files:** seen when saving and reloading files the tests build, with no real file at
  hand.
- **nif.xml:** nifly's code disagrees with [nif.xml], the community's reverse-engineered format
  spec. The tests assert nif.xml's layout, so they prove the bindings follow nif.xml, not that
  real files match it. Unpatched nifly reads and writes these fields symmetrically, so a plain
  round trip doesn't show the bug.

Fixes backed only by nif.xml or built files should be checked against real files from the
affected games when they're available. Code links go to the pinned nifly commit, and
nif.xml links to the lines that disagree with it, at develop as of 2026-11-20.

`fix_read_lighting_shader_types` does this for Fallout 76 and Starfield shader types that nifly

there says these games dropped type 3, and [nif.xml][x-shader-type] agrees for Fallout 76
(it has no Starfield entry). On built files, an Eye shader came back as Cloud.

### `*Restore` guards: save must not change the file

Saving shouldn't change the file in memory: a caller who saves twice, or keeps editing after a
save, should work on the same data. Each guard records some state before nifly's `Save` and puts
it back afterwards. There are two kinds:
- **Undoing nifly's changes:** nifly's write code changes the blocks it writes. Left alone, the
  next save could lose data the first kept.
- **Adjusting for the save:** nifly writes correctly only with a value the file in memory
  shouldn't keep. The guard sets it for the save and restores it.

| Guard | Kind | What it handles | nifly code | Evidence |
|---|---|---|---|---|
| `LightingTypeRestore` | Undo | Fallout 76 and Starfield: writing lowers each lighting shader's type by one in memory. The data written is still wrong, which the Rust docs say (`set_shader_type`); the guard undoes only the change in memory. | [Shaders.cpp:412-421][shader-type], then the [type's fields][shader-fields] | Built files: a HairTint shader saved a file nifly couldn't load again. Not tried in either game. |
| `TangentFlagRestore` | Undo | Oblivion: writing clears each `NiGeometryData`'s tangent flag, so the next save deletes the tangents' `NiBinaryExtraData` and renumbers blocks. | [Geometry.cpp:55-57][tangent] | Real files: nifly's `TestNifFile_Skinned_OB` shrank from 140,607 to 108,034 bytes on its second save. |
| `SourceTextureRestore` | Adjust | Sets the pixel data flag that `SourceTextureFactory` sets on load, for textures added since, so nifly writes their pixel data ref. | [Objects.cpp:281-288][src-tex] | As `SourceTextureFactory` |

The guards are C++ RAII objects in `save_nif`, not Rust code around the call, for two reasons:
- **The state is inside one C++ call:** the guards set and restore it around nifly's `Save`.
- **They must run if `Save` throws:** a Rust writer's `io::Error` reaches C++ as an exception,
  and destructors still run.

`Save` may also optimize away unreferenced blocks. So each guard looks its blocks up again by
address among the remaining ones instead of dereferencing pointers it saved.

Where the bindings write a block themselves, a guard isn't needed: the writer can use the
adjusted value without storing it, as `write_mesh_data` does with the mesh scale.

## Documentation and tests

- **Docs describe the bindings, not nifly:** public docs in `src/` never mention nifly or C++,
  so the crate reads as one library.
- **Generated docs, checked by tests:**
  - Each module ends with its type hierarchy (`tests/it/type_hierarchy.rs`).
  - Each type's page lists its supertypes, its subtypes and every `View`/`Edit` method that
    works on it (`docs/types/*.md`, `tests/it/type_docs.rs`).
  - These tests fail when the docs are stale and regenerate them with an environment variable.
- **One test per method:** each exposed method has an integration test in `tests/it/`,
  against `assets/*.nif` and nifly's own test files. The fixes above are tested by saving,
  reloading and comparing.

Each workaround above patches a nifly bug from outside. Fixed in nifly, the workaround could go,
and other nifly users would get the fix too. The bugs backed only by nif.xml should be checked
against real files from the affected games before they're reported.
